## Product goal
A family party game for 3–50 players, optimized for 5–25. Participants scan a QR code, enter a display name, answer eight private questions about themselves, then play a synchronized multiple-choice quiz about each other. A living-room TV shows questions, countdowns, answer reveals and standings. A separate host interface controls the game. No player accounts, email addresses or installations. All names and answers in examples are fictional sample data, never hardcoded production content.

## MVP defaults (host configurable)
- Title: Family Face-Off; themes: classic game show and Thanksgiving. Responsive, accessible, readable from across the room.
- 8 personal questions: 4 common and 4 randomly assigned from the bank; free text, max 120 characters; allow replacement prompts from unused bank. Every player must complete eight before being marked ready.
- 20-second question timer; choices A–D; single correct answer; 20 quiz rounds by default, 1–80 configurable subject to valid question availability; target equal exposure across players.
- 1000 points per correct answer; optional speed bonus 0–500, off by default. No streak or final bonus in MVP. Subject of a question sits out and earns no points; equalize eligible opportunities where possible. Incorrect or missed answer scores zero. Ties share rank.
- Manual host advancement by default, optional automatic reveal after everyone eligible locks or deadline expires; optional automatic next round after 8-second reveal. Host can pause/resume and skip rounds. Show leaderboard after every reveal.
- Use only submitted answers as truth. AI is optional and must never change correct answers. No AI API key needed to play.

## State machine
Game phases LOBBY -> PREPARING -> QUESTION -> REVEAL -> QUESTION ... -> FINISHED; PAUSED is represented by paused_at and remaining_ms during QUESTION; CANCELLED optional. Host start locks roster and questionnaire snapshots; require at least 3 ready players, explicitly exclude unready players only after host confirmation. PREPARING generates and validates rounds, then host starts first question. Host can retry generation if it fails; deterministic fallback always available. At QUESTION create server deadline; answers accepted only for current round, eligible player, before deadline and not paused. First valid submission wins. Reveal computes scores once. Next opens new round with fresh deadline. Skip marks round void, awards nothing, optionally replace with unused round. End game displays final standings. Reconnect does not change eligibility. All transitions transactional with game row lock or compare-and-swap version. Every mutation idempotent or returns explicit conflict. Automatic transitions are evaluated by authorized polling requests or explicit host actions, not process timers; only due transitions may execute; if nobody polls, transition occurs on next request. Never auto-advance multiple unseen rounds based on old deadlines. Use database clock for authoritative cutoff. Pause/resume preserve remaining duration. On expired question reject new answers even if reveal has not yet run.

## API contract
All endpoints under `/api`; JSON errors `{error:{code,message}}`; 400 validation, 401 unauthenticated, 403 unauthorized, 404 missing, 409 phase/duplicate conflicts, 429 rate limited. Use Zod for all inputs and shared DTO types. Mutation requests use POST/PATCH/DELETE, validate same-origin Origin where applicable, secure HttpOnly SameSite=Lax cookies (Secure in production), random 32-byte session tokens hashed server-side. Keep player cookies scoped logically by game code and support concurrent sessions across games. Host and player cookies distinct. Game code is a join identifier, not authorization. Read-only display may use separate unguessable display token or host-created display link; never leak host credentials. Return minimum necessary fields.
- POST /host/login {password}; POST /host/logout
- POST /games {title,settings}; GET /games (host only); DELETE /games/:code (host)
- POST /games/:code/join {name} -> player cookie, assigned prompts; idempotent reconnect for existing authenticated player.
- GET /games/:code/questionnaire (player); PATCH /games/:code/questionnaire {answers:[{slot,answer}]}; POST /games/:code/questionnaire/replace {slot}; POST /games/:code/ready; validate exactly eight nonblank answers, immutable after start.
- GET /games/:code/state?view=player|display|host -> phase, version, serverNow, counts, currentRound public fields, deadline, own locked status, own score, eligible flag. Reveal-only fields: correctOptionId, guess distribution, named guesses (display), standings. Host view includes ready roster, not unrevealed correct options by default. Never serialize raw DB rows. No full answer bank on client.
- POST /games/:code/start -> lock roster and prepare rounds; POST /games/:code/action {action,expectedVersion} for open/reveal/next/pause/resume/skip/end; POST /games/:code/guess {roundId,optionId}; DELETE /games/:code/players/:id before roster lock.
- GET /games/:code/results -> standings after finish, host/display/player appropriately authorized.
Rate limit join/login/guess, limit body sizes, sanitize display names and text (React escaped text, no raw HTML). Avoid logging names, answers or tokens. Set no-store and noindex for private session pages. No analytics capturing personal answers.

## Quiz generation algorithm
1. Snapshot ready players and their eight answers; trim, normalize Unicode, case-fold for comparisons; reject blank, inappropriate or excessively long inputs with friendly replacement option. Do not infer age or sensitive traits. Keep questions neutral and family-friendly.
2. Build a candidate queue per player, shuffle server-side using seeded PRNG if desired for repeatable tests. Select in round-robin across subjects with randomized starting order, then randomize final sequence avoiding same subject consecutively. Balance number of subject appearances to within one where feasible. If total rounds cannot divide evenly, show eligible opportunities and optionally use accuracy as a secondary display metric; rank by points by default.
3. Type A (default): What is [name]'s [prompt]? Correct option exactly submitted answer. Distractors first from other answers to same prompt when distinct and plausible, then curated fallback options. If insufficient, optional AI supplies distractors only. Avoid near duplicates, synonyms of correct answer, answer leakage and absurd choices. For unusual free-text answers without three credible distractors, use Type B or skip candidate; never invent what a person said.
4. Type B: Who answered '[answer]' to '[prompt]'? Choices are player names. Only use when exactly one eligible roster member gave that normalized answer to that prompt, and at least four distinct players are available. Exclude the answer's author from scoring. Avoid implying others answered prompts they did not receive; use wording 'Who submitted this answer?'. With three players, stick to Type A.
5. True/false and matching are optional later features, not MVP. Shuffle option order server-side; store stable option IDs unrelated to correctness. Validate exactly four distinct choices, exactly one correct choice, active subject, eligible roster, source answer preserved. If candidate pool too small, report achievable round count to host; do not silently repeat questions.
6. Optional OpenRouter: server only, send prompt and answer plus candidate distractors, without names or other identifying information. Host opt-in before sending family answers externally. Treat all submitted strings as untrusted data, not instructions. Ask for strict JSON `{distractors:[string,string,string]}`; validate with Zod, reject duplicates/correct answer equivalents, timeout and fallback. Batch requests where feasible; avoid per-round latency; use OPENROUTER_MODEL env, verify actual model supports requested response format. AI must not grade or generate correct answers. Default use AI off. If generation exceeds request time budget, implement resumable bounded batches; don't rely on work continuing after response on Vercel.

## Scoring and concurrency
For each eligible locked correct guess: 1000 + (speedEnabled ? floor(500 * clamp(remainingMs / durationMs,0,1)) : 0). Compute elapsed active time excluding pauses; derive from accumulated active time/remaining duration using server timestamps. Wrong/missing = 0. Subject excluded from denominator and points. Reveal transaction locks game row, checks current round and status, inserts score events with unique keys, sets revealed_at and phase/version. Duplicate reveals return same state. Guesses lock/check game phase and deadline inside transaction; race with reveal cannot create late scoring. Rankings: descending total, shared rank on ties, alphabetical for stable rendering. Display correct answers, eligible rounds, accuracy; no speed tie-break unless host opts in later. All eligible players receive zero score event for missed rounds if using score events for denominator.
